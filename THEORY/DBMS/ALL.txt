1. Illustrate INSERT, DELETE, UPDATE, ALTER & DROP Commands in SQL
INSERT
Used to add new records into a table.
INSERT INTO Student (SID, Name, Age)
VALUES (101, 'Rahul', 20);
DELETE
Used to remove records from a table.
DELETE FROM Student
WHERE SID = 101;
UPDATE
Used to modify existing records.
UPDATE Student
SET Age = 21
WHERE SID = 101;
ALTER
Used to change the structure of a table.
ALTER TABLE Student
ADD Address VARCHAR(50);
DROP
Used to delete an entire table.
DROP TABLE Student;

2. Informal Design Guidelines for Relational Schema Design
1. Clear Semantics of Attributes
Attributes in a relation should represent facts about one entity.
2. Reduce Redundancy
Avoid duplicate storage of data.
3. Minimize Update Anomalies
Design relations to avoid insertion, deletion, and modification anomalies.
4. Avoid Excessive Null Values
Relations should not contain many null attributes.
5. Avoid Spurious Tuples
Decomposition should be lossless.
Example:
Bad Design:
EmpID	EmpName	DeptName	DeptLoc
Good Design:
Employee(EmpID, EmpName, DeptID)
Department(DeptID, DeptName, DeptLoc)

3. Functional Dependency and Inference Rules
Functional Dependency
A functional dependency (FD) X -> Y means that if two tuples have the same value for X, they must have the same value for Y.
Example:
StudentID -> StudentName
Armstrong's Inference Rules
1. Reflexivity
If Y ⊆ X then
X -> Y
Proof: Since Y is part of X, same X implies same Y.
2. Augmentation
If
X -> Y
Then
XZ -> YZ
Proof: Adding same attributes on both sides preserves dependency.
3. Transitivity
If
X -> Y
Y -> Z
Then
X -> Z
Proof: X determines Y and Y determines Z, therefore X determines Z.
Derived Rules
Union
X -> Y
X -> Z
---------
X -> YZ
Decomposition
X -> YZ
---------
X -> Y
X -> Z
Pseudotransitivity
X -> Y
WY -> Z
---------
WX -> Z

4. Types of Update Anomalies
Insertion Anomaly
Cannot insert department information without employee data.
Deletion Anomaly
Deleting the last employee in a department removes department information.
Modification Anomaly
Changing department location requires updates in multiple rows.
Example:
| EmpID | EmpName | Dept | Location |
| ----- | ------- | ---- | -------- |
| 1     | Ram     | IT   | Mumbai   |
| 2     | Ravi    | IT   | Mumbai   |
Changing Mumbai to Pune requires modifying multiple rows.

5. Assertion and Triggers
Assertion
A condition that must always remain true.
CREATE ASSERTION Salary_Check
CHECK (NOT EXISTS
(SELECT *
 FROM Employee
 WHERE Salary < 10000));
Trigger
Executed automatically when an event occurs.
Example:
CREATE TRIGGER Salary_Audit
AFTER UPDATE ON Employee
FOR EACH ROW
INSERT INTO Audit
VALUES (NEW.EmpID, NEW.Salary);
Whenever salary is updated, a record is inserted into Audit table.

6. ACID Properties
A – Atomicity
Transaction executes completely or not at all.
C – Consistency
Database remains in valid state.
I – Isolation
Concurrent transactions do not interfere.
D – Durability
Committed data remains permanently stored.
Example:
Bank transfer ₹1000 from A to B.
Atomicity -> both debit and credit occur.
Consistency -> total balance unchanged.
Isolation -> other transactions cannot see partial results.
Durability -> committed transfer survives system crash.

7. Two-Phase Locking (2PL) Protocol
Used for concurrency control.
Phase 1: Growing Phase
Transaction acquires locks.
Phase 2: Shrinking Phase
Transaction releases locks.
No new lock can be acquired after releasing one.
Example:
T1:
Lock(X)
Read(X)
Write(X)
Unlock(X)
Guarantees conflict-serializable schedules.
---
8. Define Schedule with Example
A schedule is the order in which operations of multiple transactions are executed.
Example:
Transaction T1
Read(A)
Write(A)
Transaction T2
Read(B)
Write(B)
Schedule:
T1: Read(A)
T2: Read(B)
T1: Write(A)
T2: Write(B)
This schedule interleaves operations of T1 and T2.

9. System Log in Database Transaction
A system log records all transaction activities.
Log entries:
<START T1>
<T1, A, 5000, 4000>
<COMMIT T1>
Where:
Transaction ID = T1
A = modified item
5000 = old value
4000 = new value

10. NoSQL and CAP Theorem
NoSQL
NoSQL means "Not Only SQL".
Features:
Flexible schema
High scalability
Distributed storage
Examples:
MongoDB
Cassandra
Neo4j
CAP Theorem
A distributed system can provide only two of:
Consistency (C)
All nodes return same data.
Availability (A)
Every request gets response.
Partition Tolerance (P)
System works despite network failures.
Examples:
CP: HBase
AP: Cassandra
CA: Traditional RDBMS

14. Equijoin and Natural Join
Equijoin
Join based on equality condition.
SELECT *
FROM Employee E, Department D
WHERE E.DeptID = D.DeptID;
Result contains both DeptID columns.
Natural Join
Automatically joins matching attributes.
SELECT *
FROM Employee
NATURAL JOIN Department;
Result contains only one DeptID column.

15. Normalization
Normalization reduces redundancy and anomalies.
First Normal Form (1NF)
No multivalued attributes.
Not 1NF:
SID	Phone
101	9876,1234
1NF:
SID	Phone
101	9876
101	1234
Second Normal Form (2NF)
Must be in 1NF and no partial dependency.
Example:
(StudentID, CourseID) -> Grade
StudentID -> StudentName
Move StudentName to separate table.
Third Normal Form (3NF)
Must be in 2NF and no transitive dependency.
Example:
EmpID -> DeptID
DeptID -> DeptName
Decompose into:
Employee(EmpID, DeptID)
Department(DeptID, DeptName)
---
16. Functional Dependency and Minimal Cover
Algorithm for Minimal Cover
1. Ensure single attribute on RHS.
2. Remove extraneous attributes from LHS.
3. Remove redundant dependencies.
Given:
E = { B->A, D->A, AB->D }
Step 1
Already single RHS.
Step 2
Check AB->D
Since:
B->A
AB->D
A is extraneous in AB->D.
Therefore:
B->D
Step 3
Now set becomes:
{ B->A, B->D, D->A }
Since:
B->D
D->A
By transitivity:
B->A
is redundant.
Minimal Cover
M = { B->D, D->A }

17. SQL Queries (Sailors-Boats-Reserves)
(i) Colors of boats reserved by Alber
SELECT DISTINCT B.color
FROM Sailors S, Boats B, Reserves R
WHERE S.sid = R.sid
AND B.bid = R.bid
AND S.sname = 'Alber';
(ii) Sailor IDs with rating ≥ 8 or reserved boat 103
SELECT sid
FROM Sailors
WHERE rating >= 8
UNION
SELECT sid
FROM Reserves
WHERE bid = 103;
(iii) Names of sailors who have not reserved a boat containing "storm"
SELECT sname
FROM Sailors
WHERE sid NOT IN
(
    SELECT R.sid
    FROM Reserves R, Boats B
    WHERE R.bid = B.bid
    AND B.bname LIKE '%storm%'
)
ORDER BY sname ASC;
(iv) Sailor IDs with age > 20 and not reserved a boat containing "thunder"
SELECT sid
FROM Sailors
WHERE age > 20
AND sid NOT IN
(
    SELECT R.sid
    FROM Reserves R, Boats B
    WHERE R.bid = B.bid
    AND B.bname LIKE '%thunder%'
);

18. SQL Queries
(i) Create table statement for Reserves
CREATE TABLE Reserves
(
    sid INTEGER,
    bid INTEGER,
    day DATE,
    PRIMARY KEY (sid, bid, day),
    FOREIGN KEY (sid) REFERENCES Sailors(sid),
    FOREIGN KEY (bid) REFERENCES Boats(bid)
);
(ii) Find all information of sailors who reserved boat 101
SELECT *
FROM Sailors
WHERE sid IN
(
    SELECT sid
    FROM Reserves
    WHERE bid = 101
);
(iii) Names of sailors who reserved at least one boat
SELECT DISTINCT S.sname
FROM Sailors S, Reserves R
WHERE S.sid = R.sid;
(iv) Names of sailors who reserved a red boat
SELECT DISTINCT S.sname
FROM Sailors S, Reserves R, Boats B
WHERE S.sid = R.sid
AND R.bid = B.bid
AND B.color = 'Red';
(v) Average age of sailors for each rating level
SELECT rating,
       AVG(age) AS Average_Age
FROM Sailors
GROUP BY rating;
